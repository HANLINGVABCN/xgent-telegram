# 轻量多会话：各端独立选择，历史继续共享

## 使用方式

一件事拥有一份独立上下文，复用同一套模型调用、Agent 执行和 SQLite 数据库。每个对话有独立执行槽：同一对话按序运行，不同对话可同时生成回复和执行命令。

- **Telegram 独立保持当前会话。** 使用 Bot 的 `/chats`、`/new [名称]` 主动选择；网页或 CLI 切换不改变 Bot 的下一条消息归属，也不再向 Bot 广播切换通知。
- **Web、Bot 和每个终端独立选择。** 每个 CLI/TUI 进程首次打开以当时 Web 当前会话为起点，之后只跟随本终端操作；不把终端选择写成全局配置。网页会话列表继续用小型「Bot 当前」标记显示 Bot 选择，不改变排序或代表忙碌。
- 聊天记录仍按会话共享。Web／CLI 在 Bot 当前会话里发起普通聊天时，正文、附件和回复继续同步到 Telegram；其他会话的普通聊天以及网页菜单、配置等管理回执不主动投递。
- 初始镜像决定在回合接纳时固定。**Web 发起的运行中回合**另有投递订阅：Bot 切入时，补齐当前尚未结束回复的已有片段，随后沿相同逻辑消息 ID 编辑；不补过去回复，重复切入不重新建消息。已订阅的回合完整结束，切走后按原规则标明来源；CLI 初始路由规则不变。
- 定时任务仍按原会话执行并主动通知，包括已归档会话；不自动改变两端选择。被永久删除会话的任务会终止并删除。
- 归档或删除 Bot 当前会话后，Bot 进入「未选择」状态。下次交互提供选择／新建入口，普通消息或附件不会记录、不会改投其他会话；选择后不自动重发之前的输入。恢复会话也不会自动绑定。
- Web 归档当前会话时仍回退到最近活动的可用会话，没有则新建。Bot 或终端的当前会话被归档／删除后则等待重新选择；不会因为恢复会话而自动重新绑定。停止操作仍匹配具体 `run_id`。

## Web 分组与对话菜单

- 默认打开“默认分组”，沿用原“未分组”的 `ungrouped` ID；启动时更新保留组的旧名称，不迁移对话归属、不清除已有置顶。分组下拉顺序为默认分组、全部对话、其余分组。
- “全部对话”是跨分组视图，不是独立分组。它把各组的置顶对话汇总到顶部；组内置顶始终属于对话实际所在的组，移动到其他组后清除原置顶。切换分组只筛选侧栏，不切换当前聊天或 Bot 会话。
- 每条对话的 `⋯ → 移动到` 在桌面悬停打开右侧子菜单，空间不足时转到左侧；手机点击在菜单内展开。列出全部实际分组，当前组显示对号且不可重复选择。“全部对话”不作为移动目标；键盘右箭头进入子菜单，左箭头或 Escape 返回。
- `⋯ → 导出` 直接下载所点对话的完整记忆 ZIP，使用 Bot `/export` 的归档服务和格式，包含实际保留的旧上下文阶段与压缩记录。导出归档对话无需恢复；导出不切换当前聊天，不新增聊天消息或 Telegram 投递。缺少或无效对话 ID 时拒绝导出，不退回当前对话。
- 侧栏移除“重置上下文”按钮；原有重置接口以及 Bot／CLI 命令继续保留。

## Telegram 呈现

- 同会话普通回复不加抬头。实际投递的会话不同于 Bot 当前选择，或 Bot 暂无选择时，显示普通字 `🗂 名称 · 短 ID`；异会话的分片、附件说明、错误和任务通知都能辨认来源。
- Token、流式占位使用同一逻辑行的轻量来源信息，不另加大标题；Token 统计只保存一次，没有实际用量不编造数字。
- `/start` 删除“全局模式：常驻开启”和“记忆系统：异步SQLite + 内存缓存”，只在最后一行显示一个会话标签；`/chats` 使用自身标题，后续翻页、切换、重命名、确认和返回均编辑原卡片，不额外广播切换。
- 旧会话／旧上下文按钮只弹出原因并结束转圈，不执行、不修改卡片、不发新的聊天消息。未选择时的菜单也有独立过期保护，重启或重新打开后旧卡片不能切换新会话。
- 来源标签仅用于 Telegram 显示，不写入模型、网页正文或导出正文。
- 两端的重命名、配置录入等临时流程隔离；网页切换不取消或消费 Bot 的输入。共享配置本身仍同步。

## TUI 交互

- 顶栏左侧为会话、右侧为模型，输入框只留简洁提示符。窄终端按实际列宽截短标题，不挤压输入或增加第二行。
- `F4`、点击顶部菜单或 `/chats` 打开对话面板；搜索／选择、立即新建、改名、归档／恢复、重置和确认删除都在面板中完成。管理输入不作为聊天记录。
- 生成时允许切换、管理与提交普通文字到待发队列。A 正在执行时，B 可直接开始自己的回合；同对话的新文字仍在安全接入点按序处理。入队成功前保留草稿；未接入模型的内容只存在独立队列表。详见 [消息排队说明](message-queue.md)。
- 各会话分别保存草稿、滚动位置和消息模型，后台流式输出只更新原会话。其他会话结束给出轻量状态，不往当前正文塞带标签的回复。
- 当前会话的持久历史自动轮询刷新，默认最近 100 条；`F5` 向前扩展窗口至最多 5000 条，`/getchat` 可手动刷新，不叠加一遍重复历史。其他客户端的菜单卡片不作为新聊天插入。
- 草稿从开始输入时绑定会话与版本；清空／压缩后首次提交只提示重新确认，不默默换用新上下文。归档／删除时也不会把旧输入投到别处。
- 模型及媒体模型配置仍共享，终端回合接纳时刷新实际配置；顶部模型名与服务端配置同步。不同终端选择同一对话时会串行执行，选择不同对话时可并行调用模型。
- 待回答表单保留原会话和版本；切回同一有效上下文可继续，过期表单不能触发新的任务。普通配置录入在切换时失效，需要重新打开菜单。
- 会话选择与草稿属于本终端进程；重新打开的新终端重新取一次起始会话，不新增跨进程终端状态服务。

## 历史、上下文与导出

- `/clear` 只重置模型上下文，保留聊天历史、附件关联和定时任务；旧命令 `/clear_memory` 继续兼容但不重复列在菜单里。
- 压缩成功才原子替换模型上下文；失败、停止保留原上下文。原消息仍可查看、搜索和导出。
- 普通 `/export` 仅导出当前对话的完整历史和压缩记录，不导出其他对话。Web 对话菜单的导出同样按所点对话隔离，按「上下文阶段－状态－阶段内轮次 a/b/c」整理，按名称升序就是先旧后新：

```text
001-已清空-001a全局记忆.txt
001-已清空-001b附件路径.txt
001-已清空-001c压缩结果.txt
001-已清空-002a全局记忆.txt
001-已清空-002b附件路径.txt
002-当前-001a全局记忆.txt
002-当前-001b附件路径.txt
上下文范围.txt
```

每次 `/clear` 开启一个新阶段；压缩增加阶段内轮次，不另开阶段。编号至少补齐三位，超出时统一扩宽。`c` 只对应实际保存的完整压缩结果；未压缩尾段只有 `a`、`b`。说明文件列出已知清空时间、记录范围和数据库压缩序号。

各段普通历史记录不重复、不遗漏，管理审计保留分类。“已清空”指模型上下文，不是物理删除。旧版缺失的分界与历史不推测补造；实际留存的旧压缩快照仍可导出。

用于压缩模型的冻结快照继续使用原来的 `1a/1b/1c` 路径，且只含当前有效上下文。新导出不改写旧 ZIP、压缩引用或附件原件；永久删除的整个会话不会恢复导出。

## 隔离与共享范围

| 按会话隔离 | 继续全局共享 |
| --- | --- |
| 聊天记录、工具上下文与消息搜索 | 模型提供商和模型选择 |
| 附件自动上下文及生成图片关联 | 人设、提示词、Skill |
| 压缩链、摘要、导出与待回答表单 | 手工“用户记忆”文件 |
| 文本拼接、相册、进程内私密变量 | 文件工作目录、全局用量统计 |

私密变量仅注入对应会话的子进程，不写入进程全局环境、也不落盘。普通对话仍共享项目文件目录。命令的对话标识、交互式 shell 会话、停止事件、回复订阅及待发队列按对话隔离；一个对话停止或失败不会暂停其他对话。

## 实现与接口

- `current_chat_id` 保留 Web 选择；可为空的 `telegram_conversation_id` 保存 Bot 选择。`GET /api/workbench/conversations` 和 `conversation_state` 事件返回两者，沿用修订号与现有轮询。Bot 标记变化只更新列表，不重载聊天或丢弃草稿。
- 原有 `POST /api/workbench/conversations/{create,switch,rename,archive,restore,reset_context,delete}` 保持原行为；新增 `conversations/set_bot` 只响应「⋯ → 设为 Bot 当前对话」的明确操作。参数 `id`、目标 `generation`、`expected_bot` 校验原 Bot 选择，事务中只更新 `telegram_conversation_id`；不切换 Web/CLI、不移动任务、不改变暂停队列。未配置 Bot、目标已归档或已失效时拒绝。
- `ConversationManager` 的终端选择仅在该进程内保存，通过显式 `selector="terminal"` 管理；schema v4 新增的是共享待发消息表，不增加全局终端选择指针。
- `ConversationScope` 在记录、附件处理之前绑定；除会话、版本、回合外，保存操作来源、用途与固定的初始 Telegram 投递决定。Web 的 `WebRunDelivery` 只物化当前未结束回复，订阅后将**新操作**的投递许可写进既有出站 Op 快照；先入队创建再入队编辑，断线继续走异步出站队列，旧禁止投递记录不重新解禁。回合结束即清理订阅，模型引擎与工具接口不重新实现。
- 原有 WebOutbox、CLI 中继和出站队列保留。回放恢复原身份与投递策略；来源标签在实际发送／编辑时重新读取 Bot 选择。CLI `session_id` 仍指中继进程，不与逻辑会话 ID 混用。
- schema v7 将运行记录改为按对话保存的 `conversation_runs`。会话版本继续由全局递增序列分配；操作系统文件锁覆盖 CLI 与服务端，不在模型等待期间持有 SQLite 写事务。公共锁只用于短暂登记与文件维护，每个回合持有对应对话的锁。服务端和 CLI 需一起升级；旧程序会拒绝打开较新的数据库。
- 空闲提醒只针对 Bot 当前未归档会话；未选择时暂停。纯 Web 模式保持原规则。

## 升级、备份与回退

1. 停止服务端和所有 CLI 进程，避免新旧代码混跑；先备份 SQLite。
2. 当前 schema 为 v4。已有多会话数据库升级前生成 `*.pre-conversations-v4.sqlite3` 备份；新增队列、状态和无密钥请求回执表，不重写历史。v2 → v3 的 Bot 选择初始化仅执行一次；v1 会先执行尚未完成的 v2 步骤，不重复 `ALTER TABLE`。尚未启用多会话的更老数据库先保留 v1 迁移备份并完成迁移。
3. 后续重启保留两端各自选择，明确的 Bot `null` 不会自动重新绑定。历史、附件和任务不重新分配，不恢复被删除的默认会话。
4. 已持久化的旧切换广播不再补发；已有聊天和任务结果继续兼容回放。不批量改写或撤回已发出的 Telegram 消息。
5. 回退旧程序必须同时恢复升级前数据库；仅替换代码不安全。`.turn.lock` 不能通过删除来“解锁”，进程退出会释放操作系统锁。

测试使用临时数据库、模拟模型与隔离浏览器服务，不调用真实 Telegram，不迁移或重启线上服务。
