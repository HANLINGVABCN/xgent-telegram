# 附件、服务器上传与 Telegram 文件拼接

Web 输入框提供两个独立入口，允许一次选择多个文件；一批文件只提交一次 AI 请求。拖放和粘贴文件默认属于附件。待发送列表标出每个文件是附件还是服务器上传，允许在同一回合混合提交。

| 入口 | 图片 | 文本 | 压缩包、PDF、音视频等 | Telegram 同步 |
| --- | --- | --- | --- | --- |
| 附件 | 原生图片输入 | 完整文本输入 | 稳定服务器路径、大小、MIME、SHA-256 | 遵守现有会话同步路由；有 Bot 且可发送时同步，超限则在 Telegram 发说明 |
| 上传 | 只交路径 | 只交路径 | 只交路径 | 与附件使用相同同步规则 |

附件在当前会话的后续请求中继续可用。纯服务器上传用普通历史消息告知路径，不加入每轮自动附件上下文；文件仍能在历史和工作台中找到、下载。Agent 开启后可以使用文件工具读取这些路径。

两种入口都会同步文件到 Telegram，区别仅在交给 AI 的方式。Telegram 文件说明简短标注“网页附件”或“网页上传”；上传明确注明“仅向 AI 提供路径，未发送文件内容”。重复批次不会重复同步。

整条用户消息的文字随第一个文件一同同步；文字超过 Telegram 附言长度时，完整文字先分段发送，文件保留简短来源说明。同步用户文字和文件后才启动 AI，避免 AI 回复抢在用户文件之前出现。文件超限或 Telegram 不可用仍不撤销 Web 接收。

Web 和 Telegram 发来的图片在实时接收、接收确认及刷新后的历史中统一显示为一个用户气泡：图片在上、原始文字在下；服务器路径位于气泡底部的小字区域，过长省略，悬停可看完整路径、点击可复制。Telegram 原生照片及以文件发送的图片都保留完整附言，原有记录也按该布局回放，不把文件名、保存索引和路径混进正文，不改写模型记录和文件原件。Telegram 图片保存后会立即向 Web 发布用户消息，再处理 AI 回复。发往 Telegram 的文件不会反向镜像成 Web 中的另一条 AI 消息。

浏览器传输完成后显示“传输完成，正在保存…”，等待服务器落盘、校验和原件备份确认。接收确认只补充路径等信息，继续使用已经显示的本地图片预览，不再次下载图片。刷新或加载对话时按原图尺寸预留占位区域，图片解码完成后在原位淡入；加载失败保留位置并提供重试。重复历史同步复用现有媒体节点，实际文件版本变化时才重新加载。

Web 接收不使用 Telegram 的文件大小或数量上限。磁盘空间不足、网络中断、反向代理限制仍可能让传输失败；服务会显示实际错误。接收使用磁盘临时文件和分块解析，不把整个请求体读进内存。成功确认表示原件和历史关联已保存，不表示 AI 已回答。

附件内容展开受模型能力和请求内存预算约束。文本或图片无法直接展开时，保存原件并向 AI 明确提供路径、大小、MIME、SHA-256 和读取提示；不会因此拒绝 Web 接收。二进制文件不自动转成 Base64。切换模型时重新评估当前模型的文件数、图片能力和请求容量，路径提示不会伪称已读取内容。

Telegram 收到非图片文件后，自动进入已有的文字拼接流程；不论文字拼接设置是自动、强制开还是关闭，都使用原来的“完成，发送给AI”和“清空拼接”按钮。连续文件与文字会加入同一缓冲，用户点完成后才保存为一条附件记录并调用一次 AI。没有自动倒计时发送。接收尚未完成时不能提交半批文件；清空会清理尚未关联历史的文件。图片（包括真实内容为图片的文档）继续走独立图片/相册流程，不会提交或清空正在等待的文件拼接。

Telegram 云端接收文件仍受 `getFile` 的 20 MiB 限制，超限时会在请求下载前说明原因。Web 附件和服务器上传都以文档同步 Telegram：云端上限为 50 MiB，本地 Bot API 为 2000 MiB。超过出站限制的文件在 Web 仍然成功，Telegram 会收到标明来源、大小、发送上限及服务器路径的简短提示；没有 Bot 时不尝试投递。

`TELEGRAM_API_MODE=local_bot_api` 可明确声明本地 Bot API 能力；`cloud` 明确使用云端限制。默认 `auto` 只把 loopback 地址识别为本地服务器，任意远程代理 URL 不会自动获得本地服务器能力。远程自建本地 Bot API 需要显式设置模式，并保证文件目录映射或 HTTP 下载可用。

## HTTP 接口

- `POST /api/attachments`：附件批次。
- `POST /api/server-uploads`：只传路径的服务器上传批次。
- `POST /api/upload`：旧地址兼容入口，使用附件批次。

请求为 multipart/form-data；可重复提交 `file` 字段。可选字段为 `text`、`conversation_id`、`idempotency_key`（或 `batch_id`）、`captions`（与文件顺序对应的 JSON 字符串数组）、`modes`（与文件顺序对应的 `attachment` / `server_upload` 数组）。文件大小和哈希以实际接收字节为准。

客户端为同一批重试保留幂等键。服务同时检查文件名、顺序、大小、SHA-256、说明和模式，拒绝将同一个键用于不同内容；已保存的成功回执跨服务重启仍可由历史记录核验。HTTP 等待超时不会自动撤销服务器处理，重试同一批次不会重复写入和调用 AI。

总量超过 8 MiB 的批次自动使用 4 MiB 分块传输；这是每个 HTTP 请求的传输尺寸，不是文件大小上限。每块独立确认。遇到网络中断或代理 `HTTP 524` 时先查询服务器已接收偏移，再继续缺失部分，避免重发已经保存的字节。所有文件传输结束后，原件备份、哈希检查和附件关联在后台完成，浏览器用短请求轮询确认，不让单个 HTTP 请求长时间等待磁盘处理或 AI 回复。磁盘实际写入失败会显示原因；“正在保存校验”不等于已经确认成功。

分块协议：`POST /api/file-transfers/init` 提交文件清单、目标会话、文字、模式和幂等键；`POST /api/file-transfers/chunk/<id>?index=<文件序号>&offset=<字节偏移>` 接收原始字节；`POST /api/file-transfers/complete/<id>` 发起异步确认；`GET /api/file-transfers/status/<id>` 返回 `receiving / processing / accepted / failed` 及已接收偏移。确认成功时带持久消息描述。暂存字节和状态保存于 `xgent_storage/file_transfers/`，确认成功后删除暂存字节；失败的已传内容保留以便同一批次重试。重启不自动调用 AI，客户端明确确认后由原幂等键防止重复提交。小文件及旧客户端继续支持原 multipart 接口。

接口继续要求登录、同源校验和会话校验。文件名不作为服务器保存路径；文件内容与说明均属于用户数据。

## 验证

`tests/test_file_ingress.py` 覆盖多文件、空文件、Unicode 文件名、伪边界字节、截断清理、超过 50 MiB 的有界内存接收、HTTP 路由以及应用级拼接/同步/幂等行为。

`tests/test_file_ingress_browser.py` 使用真实浏览器检查桌面/手机输入、两种入口、混合批次与失败重试。

`tests/test_file_transfers.py` 验证中断回滚、重复块一致性、重启续传、异步接收确认与真实 HTTP 51 MiB 文件；浏览器回归模拟代理丢失首块确认的 `524`，验证按服务器偏移继续传输且只调用一次 AI。
